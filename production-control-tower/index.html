สิ่งที่เรียนรู้จาก ERP → สิ่งที่เปลี่ยนใน Control Tower

เราไม่ได้ copy หน้าจอ ERP แต่ดึง “ความจริงของ workflow” มาออกแบบระบบวางแผนอัตโนมัติใหม่

1 · Status ≠ Stateสถานะเดียวบอกความจริงของงานไม่พอ
เดิม: ดู Cutting Status แล้วสรุปว่าอยู่แผนกไหน
ใหม่: State Resolver = status + routing + last operation + material + quality + downstream state
2 · WO ต้องลงถึง OperationERP มี operation sequence และ actual hours
เดิม: วางแผนระดับ WO/Cutting
ใหม่: Scheduler วางแผนระดับ operation / work center / time slot
3 · On Hand ≠ Material Readyมี commitment, inspection, inbound และ project allocation
เดิม: มี stock = พร้อมผลิต
ใหม่: ATP/Readiness engine แยก required, committed, available, shortage, PO ETA
4 · Calendar ≠ Capacityต้องรู้ resource และ standard time ด้วย
เดิม: วันทำงานเป็นฐาน
ใหม่: capacity = resource × shift × availability; load = standard minutes × remaining qty
5 · Version/Rule สำคัญพอ ๆ กับ DataERP behavior เปลี่ยนได้ตาม version / option
เดิม: logic ซ่อนใน query / program
ใหม่: effective-dated rule + rule version + evidence + approver + audit
6 · Snapshot ต้องมี Lineageข้อมูลคนละช่วงเวลาห้าม join แบบไม่รู้ context
เดิม: extract หลายไฟล์เหมือนเป็นชุดเดียวกัน
ใหม่: source_batch / extract time / valid period / DQ state เป็น first-class fields
7 · Planner ไม่ควรไล่เช็กทุก OrderERP ให้ raw operational evidence ได้
เดิม: Planner เปิดหลายหน้าจอและรวมข้อมูลเอง
ใหม่: system pre-computes plan + exceptions; Planner เป็น supervisor ของ automation
8 · AI ไม่ใช่ Schedulerdeterministic constraint ต้องมาก่อนคำแนะนำ
เดิม: เสี่ยงให้ AI เดาแผน
ใหม่: Rules/Solver คำนวณก่อน → AI อธิบาย/เสนอ → Human Gate → Publish

Automation Architecture

แยก ERP ออกจาก Planning Intelligence ชัดเจน เพื่อให้ระบบวางแผนเร็วขึ้น แต่ยัง trace กลับไปยัง source ได้ทุกจุด

ERP / Sources

Demand, WO, Routing, Material, Actual, Quality

Source Batch

Immutable ingest + lineage + data quality

Operational Model

Normalized order / routing / ATP / execution

Rules & Solver

Readiness, capacity, precedence, risk, schedule

Control Tower API

Plan, exception, scenario, evidence

AI Copilot

Explain, compare, recommend, summarize

Human Gate

Approve → governed publish → monitor drift

Deterministic Core

สิ่งที่กระทบ feasibility ต้องเป็น rule/solver ที่คำนวณซ้ำได้ เช่น precedence, material, capacity, due date, freeze, quality hold

AI Layer

ใช้ AI หลังจากมีผลคำนวณแล้ว เพื่ออธิบายเหตุผล สรุปผลกระทบ จัดอันดับ exception และเสนอ action — ไม่ให้ AI เป็นผู้กำหนดข้อเท็จจริงของแผน

Public-safe design: หน้า Web นี้แสดง Architecture และ Planning Concept เท่านั้น รายละเอียด ERP object/version/table/security เก็บใน Private ERP Architecture repository แยกต่างหาก
