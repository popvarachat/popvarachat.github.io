จาก AI ที่ตอบคำถาม → AI ที่ช่วยดูแลระบบ IT

ลองนึกถึงบริษัทที่มี Wi-Fi, Switch, Server และคอมพิวเตอร์หลายร้อยเครื่อง ถ้าเครื่องสำคัญหยุดทำงาน เราอยากให้ AI ตรวจพบเอง → ตรวจว่าเสียจริง → แจ้งคนที่เกี่ยวข้อง → ช่วยแก้ไข → ตรวจจนมั่นใจ โดยไม่ต้องรอให้คนมาคอยสั่งทุกขั้น

RDC L5 จึงไม่ได้ตั้งใจเป็นแค่ Chatbot แต่กำลังพัฒนาเป็น Multi-Agent System ที่สั่งเครื่องมือได้จริงและเก็บหลักฐานทุกการตัดสินใจ

ทำไมเราต้อง Sandbox ก่อน?

การทดลองกับ Network ของบริษัทโดยตรงมีความเสี่ยง เราจึงสร้างสนามทดลองที่ใช้ Notebook เก็บข้อมูล → RDC ส่งข้อมูล → PC เป็น Data Hub จำลอง NAS และให้ Agent จำลองทำงานร่วมกัน

ผลดี: ทดลองการส่งข้อมูล Queue, Incident และการตัดสินใจได้ โดยไม่ไปแก้ค่าของ Network Production

ใครทำหน้าที่อะไร?

Notebook: อ่านสถานะและสร้าง Evidence

RDC Orchestrator: จัดคิวงาน เลือกเครื่องมือ ส่งข้อมูล

PC / Mock NAS: เก็บ Baseline, Queue, Incident และ Audit

Six Mock Agents: ตรวจพบ วิเคราะห์ แจ้งเตือน จำลองแก้ไข ตรวจซ้ำ และปิดหรือส่งต่อ

การทดสอบ 2 สถานการณ์ สอนอะไรเรา?

Case A: Offline → Online

Agent จำลองพบอุปกรณ์ Offline เปิด Incident แจ้งเตือนใน Mock Inbox ทดลอง Runbook และตรวจซ้ำพบ Online จึงปิดงานเป็น closed_verified

Case B: Offline → ยัง Offline

Agent ทำกระบวนการเหมือนกัน แต่ตรวจซ้ำแล้วยังไม่กลับมา ระบบจึง ไม่ปิดงาน และส่งต่อเป็น open_escalated

ทั้งสองกรณีเป็น Simulation; ไม่มีข้อความส่ง IT จริง และไม่มีการซ่อมอุปกรณ์ Production

Bug ที่เจอจริง: Ping ไม่ตอบ ≠ เครื่อง Offline

ตอนทดสอบ PC มองว่า Notebook Offline เพราะ Ping ไม่ตอบ แต่ RDC ยังสั่ง Notebook ผ่าน MCP ได้ตามปกติ แปลว่าระบบกำลังตัดสินจากข้อมูลไม่ครบ เราจึงเปลี่ยนกฎใหม่เป็น Ping failed → Unconfirmed → ต้องหาหลักฐานเพิ่มเติม และปิด Incident แจ้งผิดพร้อม Audit

นี่คือความต่างระหว่างระบบที่ทำงานเร็ว กับระบบที่ตรวจสอบความถูกต้องก่อนตัดสินใจ

แล้ว ChatPlus กับ Teams เกี่ยวอะไร?

เมื่อ AI ตรวจเจอ Incident ต้องมีที่ส่งข้อความไปหาฝ่าย IT ซึ่งอาจเป็น Synology ChatPlus หรือ Microsoft Teams เราจึงต้องการ Notification Adapter ที่เปลี่ยนปลายทางได้ โดยไม่ต้องเขียน Incident Engine ใหม่

ตอนนี้เราทดสอบเพียง Mock Inbox ยังไม่ได้ส่ง ChatPlus หรือ Teams จริง

อะไรที่ต้องทำก่อนเปิดใช้จริง?

ต้องให้ Network Scanner ส่ง Evidence จริงอย่างต่อเนื่อง, เชื่อมช่องทางแจ้ง IT ที่รับ ACK ได้, ใช้ Runbook ที่ได้รับอนุมัติและ Rollback ได้, แล้วทดสอบ Restart / Failover / ความปลอดภัย และประเมิน SLA

เราอยู่ในขั้น Proof of Concept / Pilot ไม่ใช่ระบบ Production Self-Healing 100%

สาระสำคัญ: เรากำลังเปลี่ยนจาก “AI บอกวิธีแก้” ไปสู่ “AI ทำงานร่วมกับเครื่องจริง ตรวจสอบผล และมีหลักฐานว่าทำอะไรไปแล้ว” — แต่ยังต้องพิสูจน์ระบบจริงก่อนให้อำนาจซ่อม Network อัตโนมัติ

Workflow อธิบายการทำงาน 5 ขั้น — จาก Detect จนถึง Close

01 · SCANNER AGENT
Scan + Evidence

Notebook อ่านสถานะ Network และสร้างหลักฐานแบบ Read-only

02 · ANALYSIS AGENT
Baseline + Incident

เทียบ Snapshot เก่า ยืนยันหลายสัญญาณ แล้วเปิด Incident

03 · NOTIFICATION AGENT
IT Alert + ACK

ส่ง Evidence ไปยัง ChatPlus / Teams ผ่าน Adapter กลาง

04 · REMEDIATION AGENT
Safe Runbook

แก้ภายใต้สิทธิ์ที่อนุมัติ มี Human Gate / Rollback

05 · VERIFICATION AGENT
Recheck + Close

กลับ Online จึงปิด Incident; ไม่ผ่านให้ Escalate พร้อม Audit

เปิด Interactive Workflow แล้วเลือกโหมด Incident เพื่อดูความเชื่อมโยงกับ Agent Force, Tool Broker, Retry, Final Validator และ Human Gate
